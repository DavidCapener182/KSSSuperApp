## Controlled shared-primitives slice

`src/components/ui13/operational.tsx` and its CSS module now provide `ContextHeader`, `FactualStatus`, `FactualMetrics`, `SourceCard`, `AttentionSurface`, `ActionHierarchy`, `FilterBar`, `FormSection`, `StatePanel`, `ResponsiveRecordList` and `AuditTrail`. They are pure presentation: no source fetch, access policy, business-state mapping, action submission or optimistic success. Callers must pass authorised facts and exact source context. Status wording is caller supplied; visual tone does not reduce domain states to Success/Warning/Error. `SourceCard` requires identity, context and factual state, while freshness, metrics and action are optional. A stronger blue edge appears only when the caller deliberately sets `primary`. `ResponsiveRecordList` renders desktop and mobile views from the same supplied row array. The filter, form and action wrappers arrange caller controls but do not decide or submit anything. `StatePanel` keeps loading separate from empty and error.

This initial layer does not replace the existing `workflow.tsx` confirmation dialog or any domain submission behaviour, and it is not imported by a product route. Interactive record tabs remain domain-owned until their navigation and focus contracts are checked. Representative domain migration awaits a separately owned route choice and genuine desktop/390px browser evidence; the other UI lanes keep their files and source contracts.

## Shared proposals for UI11 / later controlled integration

1. A source-labelled summary card should present **identity + context + factual state**, with optional freshness, optional metrics and optional action. It accepts only caller-authorised facts and an exact record/version identity where relevant. It must not derive readiness or widen linked file access. Informational cards need no forced action. Reserve the stronger blue accent for deliberately primary or selected context.
2. A responsive data-list contract should require explicit mobile fields, result count, filter state and full-size row actions. Its desktop and phone representations must use the same authorised dataset.
3. A shared action-feedback contract should distinguish pending request, server acceptance, authoritative readback and refresh failure. This prototype deliberately reports no server acceptance.
4. Tabs, dialog focus return, history actor/time/version and state panels should be reviewed against the real role journeys before shared adoption.
