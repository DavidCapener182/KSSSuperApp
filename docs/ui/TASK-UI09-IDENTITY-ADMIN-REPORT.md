## Missing read contracts for a fuller grant view

The current `list_onboarding_team_people` projection returns active member Person/name, membership ID, coordinator flag and `effectiveUntil`. It omits `effectiveFrom`, grantor, grant reason and ended/revoked membership history. `list_onboarding_case_cover` returns exact case cover Person/name, start, end and reason, but omits grantor and historical revoked/expired rows. The current Site assignment API returns stable Person ID, finite period, grantor ID and reason for one manageable Site; it has no safe Person name in that response and no organisation-wide Super Admin grant overview. Role assignment has a guarded write route but no equivalent permission-aware role-history read for a named Person. These omissions prevent a truthful single Person → role → exact Site → finite capability → expiry/grantor view.

Proposed separate read-only contract: a Super Admin-only, server and database scoped `GET /api/access/people/[personId]/grant-review` returning the stable Person ID and safe display name, active and historical role assignments, exact Site assignments with Site ID/name and lifecycle, and separately typed capability grants with source ID, effective interval, grantor Person ID/display name, reason, revocation and source link. Each domain must explicitly authorise its own rows; private evidence metadata and file bytes must be excluded. Office users should retain only their existing Site/team/domain-specific views. This needs a bounded product/security task before implementation, including direct RLS and negative tests. It is not a request to infer grant effects from a universal table or to add a broad client-side join. Working title: **Person Access & Grant Review Projection**. David suggested `TASK-02C`, but that ID already names the accepted document-review Task hand-off in this repository; assign a free identifier when the later task is briefed. The principle is one review screen over independently authorised grant facts, never one universal permissions ledger.
