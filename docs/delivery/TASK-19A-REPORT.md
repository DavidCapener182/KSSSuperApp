## Storage revocation finding and close-out

Close-out probes reproduced the old-key issue through the actual authenticated Storage endpoint. After replacement, the database access check and application file route denied the old v1 immediately, but a Staff user who had previously downloaded its object received HTTP 200 with `cf-cache-status: HIT` for at least 120 seconds. The response sent `Cache-Control: public, max-age=0` when uploaded with the same `cacheControl: "0"` setting already used by the app. A fresh session for the same Staff Person also received the cached bytes. A different Staff Person and an unauthenticated caller could not retrieve the object. Thus this is an authenticated CDN cached response persisting after the underlying RLS decision changed; it is not an issued signed URL or a browser cache hit. The measured residual window is **at least 120 seconds; its maximum remains unestablished**. Setting browser cache control to zero did not remove it.

The browser and public app API do not disclose raw Storage object keys, and the file route reauthorises each request. This reduced exposure but did not invalidate a key already learned by an authorised Staff user under the earlier policy. Supabase documents that Smart CDN caches authenticated and signed responses and that `cacheControl` controls browser caching ([CDN behaviour](https://supabase.com/docs/guides/storage/cdn/smart-cdn)). The earlier measured residual window was **at least 120 seconds; its maximum was not established**. No CDN grace period is accepted as the operational revocation model.
