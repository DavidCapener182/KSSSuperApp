## Proposed assessment model

- Give an Assessment a stable identity and each draft/published AssessmentVersion a separate opaque ID, parent CourseVersion ID and monotonic version number. The first bounded model uses fixed, ordered single-choice and multiple-choice questions only. Each question has stable version-local ID, plain-text prompt, ordered plain-text options and a nonempty keyed option set; multiple-choice grading requires an exact set match. No free text, partial credit, randomisation, AI grading, media, bank import or proctoring.
- An AssessmentVersion draft has a revision and may be edited or explicitly abandoned by its authorised author. A publisher checks the expected revision, validates the full question/options/key set and policy, and seals a canonical snapshot and hash. Publication freezes question selection/order, keyed answers, scoring weights/method, pass mark, allowed attempts, retake delay/window, time limit if any, interruption/abandonment rule and correct-answer disclosure policy. No silent defaults for KSS policy values. Changing any of these makes a **new** AssessmentVersion. Preserve all old snapshots and hashes. A version must be linked to an already published, unretired CourseVersion; publishing an assessment must not mutate that sealed CourseVersion.
- An exact CourseVersion may have one active published AssessmentVersion for new attempts in this slice. Publishing a new assessment version moves only that current pointer. Existing Attempts retain their own AssessmentVersion. Draft previews are restricted to authorised assessment administrators and use synthetic data; preview cannot create a learner Attempt or result. An explicit retirement blocks new starts, retains history and triggers review of in-progress attempts under the approved interruption policy. No automatic reassignment or CourseVersion update.
- Keep the question key and scoring policy in a database-private snapshot or equivalently guarded storage. The Staff assessment-delivery projection returns prompts and options without keys, per-option correctness, scoring metadata that reveals answers, or privileged preview fields. Do not embed secrets in server-rendered HTML, hydration data, network JSON, error messages, logs, analytics or export. Answer disclosure after submission is a separately approved policy choice; default proposal is score/pass outcome without correct answers.

## Attempt lifecycle and grading

1. Opening the assessment introduction or reading questions without an explicit **Start attempt** action makes no Attempt and consumes no allowance. Start requires an active authenticated Security Staff Person who owns an active Assignment for the exact published, accessible CourseVersion and active AssessmentVersion. The transaction locks/rechecks Assignment state, version retirement, current assessment pointer, eligibility and attempt allowance, then allocates one Attempt ID with server start time and pinned IDs. A stale version selection fails. One open Attempt per Assignment/AssessmentVersion; a retry with the same request key returns that same ID.
2. `IN_PROGRESS` answers may be saved as a mutable working draft with optimistic Attempt revision and exact question/option validation; drafts are not graded evidence. Decide with David whether draft persistence is needed for the first slice. A refresh/reconnect resumes the same open Attempt. Server deadlines, if approved, use server time, never browser clocks.
3. Explicit **Submit attempt** requires expected Attempt revision and an idempotency key. A single guarded transaction locks the Attempt, validates owner, Assignment state, pinned versions, allowed question IDs and option IDs, required answers and timing rule, then writes an immutable submitted answer snapshot, submitted-at server time and deterministic grade computed solely from the pinned sealed key/policy. Store raw points, possible points, calculated score, pass threshold, result `PASSED` or `FAILED`, algorithm identifier/version and snapshot hash. Do not trust a client score, pass flag, question text or answer key. The submission and grade commit together; no submitted-but-ungraded success state.
4. The same submit key and identical payload returns the same result; changed payload under that key fails. A different key after submission returns the existing result only when the full payload matches the sealed submission; a changed answer fails and never overwrites it. Two concurrent submissions serialize to one winner; the loser receives the committed same result only for identical content, otherwise a conflict. A stale revision cannot silently grade.
5. Interrupted network requests can safely retry their request key. User abandonment is an explicit attributable `ABANDONED` terminal transition with reason and server time; no score/pass result. Closing a tab alone does not abandon. A server-enforced expiry, if approved, records `EXPIRED` with the fixed deadline and immutable event. Decide whether abandoned/expired Attempts consume allowance. Retake starts a **new** Attempt ID after the approved limit/interval checks; failed Attempts remain visible. No pass erases a prior failure. Cancellation/supersession of the Assignment blocks new starts and submissions; past submitted results remain readable. The handling of an open Attempt on cancellation, supersession or retirement needs the decision below and must be transactional/explicit.
6. Later AssessmentVersion publication never regrades or reinterprets a previous Attempt. Corrections are outside the first implementation unless David approves a distinct, reasoned append-only regrade/void process with separate authority, old/new result visibility and no mutation of original answers. A pass is a factual assessment result only.

## David's fixed implementation decisions — 24 September 2026

The earlier open decisions below are resolved by David's approval; this section controls the build.

- `ASSESSMENT_AUTHOR` and `ASSESSMENT_PUBLISHER` are separate finite named grants for active Office Admin Persons, granted/revoked by Super Admin. One Person may hold both. Super Admin role alone provides oversight and grant administration, never assessment actions. Existing Training capabilities grant no assessment authority.
- First model: plain-text single-choice/multiple-choice only, 1–25 required questions, 2–6 options/question, equal weight, exact keyed answer/set, no partial credit. Store integer correct/total points and percentage `correct / total × 100`; published pass threshold is exactly 80%.
- Maximum three **submitted** Attempts per Assignment + AssessmentVersion. Failed submission consumes one. Retake starts no earlier than 30 minutes after the prior failed submission, measured by server time. No broader window. A later AssessmentVersion has an independent allowance and does not regrade or merge older Attempts.
- Persist draft answers server-side with expected revisions. Start, save, resume, submit and explicit abandon are the only lifecycle actions. Passive opening creates nothing. No time limit, countdown or automatic expiry. Abandonment preserves history without consuming submitted allowance; only one open Attempt per Assignment/AssessmentVersion.
- An open Attempt survives publication of a newer AssessmentVersion. It may finish while its Assignment stays ACTIVE and its pinned CourseVersion and AssessmentVersion remain accessible/unretired. Cancellation, supersession or retirement blocks further answer/submission actions, preserves the draft/history and records an attributable source-state event. No automatic new Attempt.
- Publishing AssessmentVersion v2 changes the current pointer for **new** Attempts on existing active Assignments to the same CourseVersion. Submitted v1 results remain v1; v2 allowance is separate.
- After submission Staff sees attempt number, exact AssessmentVersion, submission time, percentage, PASSED/FAILED, remaining submitted attempts and earliest permitted retake when applicable. No correct answer, option correctness, question feedback, key or hidden grading metadata is disclosed. Test API, HTML, hydration, errors, logs and browser data for leakage.
- No Operations manager assessment projection, broad learner search, ranking or leaderboard. Authorised Training/Assessment administrators see only minimum operational Attempt history.
- No manual regrade, override, void workflow or accommodations engine. Submitted answers/results are immutable. Any demonstrated need becomes a later proposal.
- A passing Attempt is a factual result only. It changes no Assignment, Completion, certificate, onboarding, credential, candidate/eligibility, pay or payroll state. TASK-20E remains separately approved future work.
