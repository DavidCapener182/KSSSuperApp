## Purpose and present contracts

The purpose is to coordinate the work from an authorised client handover toward a proposed go-live without mistaking a CRM result for an operational decision. The accepted 05A/05B contract retains one `crm_organisations.id` from Prospect to Client, terminal `WON` Opportunity history and guarded CRM Tasks. The accepted 06A contract retains `sites.id`, `site_client_links.id`, `operational_events.id`, an optional exact Won Opportunity on an Event, and independent Site/Event creation guards. 08A provides stable `site_services.id` under an exact Site/Client link. 08C, 09B and active 10B have distinct allocation, attendance and worked-time authority. None of those records is a mobilisation or a readiness verdict. 09B was implemented at `2cef90b` and separately accepted at `1e63979`; 10B owns Event worked-time and must not be altered here. The current shared tree contains unrelated in-progress files; this proposal owns only this document.

The master R09/R11 describes template-driven mobilisation, but the approved CRM conversion only changes the existing Organisation relationship and does **not** create mobilisation. `WON` means a commercial pipeline outcome. It does not establish signed contract, PO, agreed rates, billing entitlement, deployability, legal compliance or go-live. This proposal does not implement contracts, finance, eligibility, document approval, staffing allocation, equipment custody or source module setup.

## Identity and lifecycle

Propose `mobilisations.id` as a stable UUID with required `organisation_id → crm_organisations.id`, optional `source_opportunity_id → crm_opportunities.id`, `owner_person_id → people.id`, target go-live **date** (Europe/London business date, nullable until known), controlled title/scope, creator, timestamps and integer revision. The Organisation ID is never copied as a new Client. The Opportunity ID is exact provenance: at creation it must belong to that Organisation and be `WON`; no name matching. A Client mobilisation may have no Opportunity. More than one mobilisation per Organisation or Won Opportunity is allowed only as an explicit separately named scope, with a duplicate warning and actor reason; do not silently enforce one global campaign per client. The link is immutable after creation. A wrong link needs a separately approved correction path with history, never replacement in place.

Only active Office Admin or Super Admin may start a mobilisation via explicit **Authorise mobilisation** action. The transaction checks current `CLIENT` relationship, optional exact Won Opportunity and active eligible owner, records authorising actor/time and creates the initial history. CRM `WON`, visiting a page, date passing and an Event being confirmed never invoke this action. Proposed states: `PLANNING → IN_PROGRESS → GO_LIVE_REVIEW → HANDED_OVER`; `PLANNING`, `IN_PROGRESS` or `GO_LIVE_REVIEW → CANCELLED` with reason. `GO_LIVE_REVIEW` means an Office review queue, not verified readiness. `HANDED_OVER` records an explicit Office/Super operational handover decision and date, not actual Site/Event Live status, staffing approval, compliance or contract signoff. Require a reason and named decision owner for handover, with outstanding blockers and unverified source items displayed at decision time. Do not silently auto-close work or source records. Terminal correction/reopen policy is deferred.

Owner is an active Office Admin Person (or Super Admin by explicit override) accountable for the workspace, not a grant to CRM, People, Site, Event, Document or Assets. Owner reassignment needs active eligible replacement, reason, expected revision and immutable old/new history. Role loss leaves history intact and flags reassignment. Target-date changes require old/new date, actor and reason; a past target stays visible as overdue, never changes state automatically.

## Workstreams, actions and source links

Propose bounded workstream categories: commercial handover; contacts; Site/Service/Event setup; staffing; recruitment; training/induction; SOP/documents; assets/uniform; systems access; reporting; go-live and operational handover. The initial template is an immutable versioned definition selected explicitly on mobilisation creation. Template action IDs and relative due-date rules are copied as a version-bound plan, not as evidence of completion. A later template version never rewrites existing work. Office may add an ad hoc action with reason and category; source-specific work remains in its source module.

Each `mobilisation_actions.id` is stable, belongs to one mobilisation, has a named responsible `people.id`, due date, explicit state `OPEN | IN_PROGRESS | BLOCKED | DONE | CANCELLED`, optional controlled description, expected revision and creator. A workstream is a grouping of actions, not an independent verdict. An action may have typed dependencies on other action IDs in the same mobilisation; reject cycles and cross-mobilisation dependencies. A blocked dependency remains visible if a downstream action is marked done; do not silently mark downstream work complete. Explicit blockers have owner, reason, opened/resolved actor/time and resolution note; decisions have proposer/decider, outcome, rationale, time and exact optional source version. Resolution does not imply source acceptance. Factual counts show actions by state, overdue actions, unresolved blockers, unresolved decisions and unverified linked source items. Show numerator/denominator with labels where relevant, never a readiness percentage or green traffic light.

Actions may link to exact authoritative IDs using a typed allowlist: Organisation/Contact/Opportunity, Site/Site Client Link/Service/Event, existing shared Task, Person, exact Document/DocumentVersion, and future authoritative staffing, training, asset or handover records when those source contracts are accepted. Enforce FK/composite membership or equivalent transactional source checks; record link type, source ID and, for versioned evidence, exact version ID. Do not create shadow Site, Client, Person, Task or Document rows. A shared Task may be linked, but mobilisation action state never updates it and Task completion never auto-completes the action without a separately approved reconciliation rule. A linked document's audience stays at its source boundary. Store no copied document bytes, contact details, private personnel values, rates or confidential CRM notes in mobilisation fields.

The UI may offer **Create Site**, **Create Service** or **Create Event** context links that prefill authorised IDs. Each action re-authorises through the existing Site, Service or Event module, with its own ownership, status, client-link and field guards. Failure leaves the mobilisation unchanged and shows the source error. A successful source creation returns its exact ID for a separate guarded link step. No generic mobilisation RPC may bypass source authority or create an operational record directly.

The 15A Asset seam is a typed reference to its future Asset/Kit/Issue identity and source status, once accepted. Mobilisation can request and track assignment work but does not maintain stock, custody, issue/return, condition, availability or uniform size as a second ledger. A source asset record remains authoritative. The 13A Control Room and 14A handover proposals can later link exact accepted records; a mobilisation decision cannot synthesise their events. 10B Event worked-time and 09B attendance stay factual domains and do not turn into mobilisation progress or billing evidence.

## Authority, privacy and history

Initial access is Super Admin oversight and active Office Admin organisation-wide mobilisation list/detail; only Office/Super actions, with the owner responsible for triage but no exclusive data grant. Operations may receive a separately approved narrow operational handover projection later; Staff and Clients have no mobilisation workspace in 18A. Every list, search, count, detail, history, mutation and export checks role/action/record scope on the server and in database RLS. No raw CRM table read is granted through this feature. For every linked source card, independently re-authorise source access at read time; show a neutral restricted label if the current actor lacks it. A parent mobilisation permission never opens a private DocumentVersion, People profile, SIA, contract, finance or Asset record. Guessed IDs and direct table access fail. Avoid free text in audit payloads and search indexes; restrict and bound user text.

The business history is append-only and typed for create, state, owner, target date, action/dependency/link, blocker and decision changes, carrying actor Person ID, database timestamp, old/new references, reason and revision. A generic audit event records action/IDs without duplicating sensitive text. Ordinary clients cannot insert/update/delete history. No destructive delete in the UI. Preserve exact historical links even when the source record later retires, cancels, expires or changes display name; the current source state is read separately with an as-of explanation where possible. If source retention removes content, preserve only permissible metadata and a restricted/unavailable marker.

Use one guarded transaction per mutation, row lock or compare-and-swap revision, unique operation key scoped to actor and mobilisation, and stable retry result. Changed payload under the same key conflicts. Duplicate concurrent starts for the same user intent must return one ID; a genuinely new scope requires a new explicit authorisation. Dependency and link membership checks occur in the same transaction as writes. Source changes between prefill and submit are rechecked. No side effects are accepted from client optimistic UI alone.

## API/RPC and interface proposal

Add narrow guarded list/detail/history RPCs and action RPCs for authorise, change state/owner/date, create/update/cancel action, add/remove dependency, open/resolve blocker, record decision and attach/detach source link. The API routes map the current Auth subject to Person; never accept actor or role from JSON. Use bounded pagination and an identical scope predicate for count and rows. Return typed conflicts for stale revision, source changed, dependency cycle, inaccessible source and idempotency mismatch. Exact source deep links go to existing routes and perform fresh source checks. Design an integration contract for source modules to expose safe status summaries rather than handing mobilisation raw tables or private values.

Desktop Office view: client-scoped list with owner, target, state and factual counts; detail shows provenance, action table by workstream, dependency and blocker panels, decision/history timeline and source links. Review displays open blockers and unverified items before the explicit handover decision. At 390px, use stacked action cards, clear workstream headings, sticky or discoverable primary action, readable long names, no horizontal page scroll and compact count labels. Loading, empty, restricted, stale and conflict states are explicit. Follow blue/graphite/neutral design tokens and the permanent **no green** rule. Use semantic status text and icons in addition to colour; keyboard and screen-reader labels, visible focus, logical heading order, accessible dialogs, error summary and touch targets are required. Do not call an action “ready” from a count.

Regressions cover 05A/05B conversion and Tasks, 06A Site/Event guards, 08A Service lifecycle, 09B attendance and 10B worked-time boundaries. Use synthetic records only; report exact test, migration and browser results if implementation is later authorised.
