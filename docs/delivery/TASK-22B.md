## Data and publication model

Propose `operational_contact_routes` with UUID, one typed context ID, purpose, source type/ID, current published version ID, lifecycle, creator and database timestamps. A database constraint requires exactly one of Site, Site Service or Event ID. A Service route derives Site and Client link through the immutable Service relationship; an Event route derives Site and Client from the exact Event. Never accept a separately editable Client ID. For CRM source, enforce the same exact Organisation as the context; for KSS Person, check current active Person/role and approved operational route field. For a manual route, require a controlled origin description and accountable manager. Source types: exact `CRM_CONTACT`, exact `KSS_PERSON`, or `MANUAL_OPERATIONAL`.

Publish an immutable version containing only display name, role/organisation description, approved operational telephone and/or email, purpose, priority, effective instants, optional simple out-of-hours applicability, reviewed-at date, actor/time and source review marker. Require at least one method. Purpose values: `CLIENT_OPERATIONAL`, `SITE_MANAGEMENT`, `KSS_DUTY_MANAGER`, `KSS_ESCALATION`, `FACILITIES_MAINTENANCE`, `HEALTH_SAFETY`, `EMERGENCY_SITE_CONTACT`, `OTHER_OPERATIONAL`. These are route purposes, not job titles, authority or readiness states. Exclude HR, payroll, safeguarding, disciplinary and personal emergency contacts. Do not store address, DOB, private notes, personal identifiers or unrelated CRM fields in route snapshots. A published phone/email is never edited in place; correction publishes a new version under the stable route ID.

Within context + purpose + applicable window, explicitly order primary and backup routes. Database guards reject simultaneous equal priority for overlapping effective/applicability windows, including concurrent publication. A missing route is a factual gap. Store UTC instants, present Europe/London times and reject nonexistent/ambiguous local DST values unless the user explicitly selects the intended offset. A simple out-of-hours window is an applicability filter, not an on-call rota or evidence that anyone answered, worked or was available. Manual Event routes require expiry. Site/Service routes have an effective period and review date. Expired routes disappear from current views while restricted history remains. Event cancellation immediately ends Staff visibility; Site Service end prevents future duty access. Site retirement or source unavailability must not leave a silently current Staff route.

At publication, explicitly review a snapshot of permitted source fields. Later CRM changes/deactivation, KSS Person role loss or source-context changes mark `REVIEW_REQUIRED` or `SOURCE_UNAVAILABLE` through guarded checks; they never republish, choose a replacement or keep an unverified route silently current. Define the conservative behaviour: a route with source-unavailable state is absent from current Staff cards; review-required values are withheld until a Contact Manager republishes after review. A same-name replacement never inherits its route. Store source ID/version or reviewed-at marker as provenance, with no dynamic value join in Staff reads.

Append-only typed events record publication, correction, review, priority change, expiry and revocation with actor, time, old/new version IDs and controlled reason. Do not expose historical phone/email in current projections. Restricted history is available to authorised Contact Managers for their exact grant and Super Admin oversight; historical privileged reads are audited. Generic audit records contain IDs, action and changed field names, never phone/email. Routine current Staff reads use ordinary security logging, without contact values in logs. Retention and erasure policy is a pre-live decision; this synthetic implementation must not claim it is settled.

## Exact authority

`SUPER_ADMIN` grants a finite **Operational Contact Manager** authority to a named active `OFFICE_ADMIN` Person for an exact Site, Service or Event, with effective start/end and attributable grant/revoke history. Office role alone, CRM access, Event ownership, Site creator status and SiteAssignment are each insufficient to publish or correct. A grant for one context does not imply child, parent, sibling or Client-wide scope. Super Admin may publish under attributable oversight but must pass all source/context validation. Operations may read current routes within accepted operational scope and cannot publish/correct. Neither Operations nor Staff gets raw CRM Contact or private People access.

Staff current cards require their own exact `ACCEPTED` Event or Site shift allocation. Access starts 2 hours before its report time and ends 2 hours after its scheduled duty end, calculated from the accepted source duty instants. Declined/cancelled allocations never qualify; allocation or Event cancellation revokes immediately even within the time window. Site Service end prevents future duty access. An `ALLOCATED` but unaccepted response does not qualify. No relief-Staff or break-glass path in 22B. Staff see only the route assigned to the same exact context as that allocation; a Site contact is not inherited by a Service/Event card. Any later inheritance needs a separate rule and approval. Access to a route is not attendance, availability, allocation response, work or pay evidence.

Server routes and guarded database functions both resolve AuthIdentity to stable Person, check current role/action/grant and exact source record, validate source/contact relationships, and return an explicit field projection. RLS and revoked direct authenticated table/history writes provide defence in depth. Separate guarded current-list, exact-detail, history, publish/correct/review/reorder/revoke and grant operations; names/signatures to validate against current schema before implementation. Use expected revision and transaction locks for competing publications, priority checks and source-state changes. Actor/time derive in database. Guessed IDs, mismatched parent IDs and unauthorized count/search return generic denial without existence leakage. No global Staff search, export or AI tool. No values in broad analytics, notifications, push payloads or static rendering; current responses are private/no-store and revocation is checked on every read.

## Product flow

Staff open **Operational contacts** from their exact My Deployment or Site shift. A 390px one-column card shows context, purpose, display name/role, primary or backup order, applicable period, last reviewed date and only approved tel/mailto actions. A missing, expired or withheld route appears as a factual gap, without a guessed replacement or reassuring status colour. Operations gets a safe current context projection. Contact Managers and Super Admin get a context-bound management view showing source, published values, priority, windows, review date, state and immutable history; every publish/correct action previews exact Staff-visible fields and target context. The interface uses the existing blue/graphite/neutral system, no green, keyboard/focus support, readable 390px layout and no horizontal overflow.

KSS does not send messages in 22B. Tap actions hand off to the user's phone/email app. No SMS, push, automated escalation, dial attempt receipt, delivery receipt or claim that a person responded.
