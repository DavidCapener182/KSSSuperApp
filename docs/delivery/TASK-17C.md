## David's implementation decision

**Approved:** An immutable, currently effective `APPROVED` Time Away segment blocks a **new** overlapping Event or Site Shift allocation, including Staff acceptance of an allocation that became conflicted before acceptance. Leave approval **may proceed despite an existing active allocation**. It then creates an attributable `REVIEW_REQUIRED` reconciliation issue against each exact affected allocation. The operational manager resolves that issue through the existing guarded allocation workflow; approval never cancels, declines, moves, reassigns or rewrites a duty or Staff response. There is no retain-the-conflict override or silent issue closure in 17C.

The Time Away source remains distinct from Availability. Approval does not manufacture `UNAVAILABLE`, change a declaration, establish entitlement/pay or grant a scheduler access to private leave details. A pending, submitted, declined, withdrawn or finally cancelled request is not a hard block. `CANCELLATION_REQUESTED` remains effective approved leave until a separate authorised final cancellation commits. A rejected cancellation returns to approved without a gap in effect. Final cancellation ceases the **future allocation block** at commit; exact historical approval, cancellation and earlier blocked/reconciliation decisions remain visible in protected history. A cancellation must not retrospectively legitimise or alter an earlier rejected transaction.

## Exact overlap rule

Use half-open intervals `[start, end)` for both duties and leave. Overlap exists only where `leave_start < duty_end AND duty_start < leave_end`; touching boundaries are allowed. An Event duty uses the accepted requirement `report_at` to `shift_ends_at`; a static duty uses the dated demand's same fields, including report time and any following-day end. Do not substitute Event outer dates, Site Service dates, service date, display date or nominal shift start for exact duty instants.

For a whole Europe/London day `D`, derive `[D 00:00 Europe/London, (D+1) 00:00 Europe/London)` as two separately resolved instants. Multiple inclusive whole dates end at midnight after the last date. This allows 23-hour and 25-hour daylight-saving days. Partial segments use the 17A/17B stored exact instants and their entered local context; ambiguous or nonexistent local input was rejected at entry and is never silently normalised by the guard. Split cross-midnight partial input into dated segments as 17A specifies. Evaluate each immutable approved segment, or a canonical non-overlapping union, against the entire duty interval. A night duty overlaps leave on either calendar date when the instants intersect. Distinct segments/requests must not multiply one allocation into multiple reconciliation cases without explicit distinct provenance.

## Transactional authority and precedence

The accepted 08A guard `private.person_allocation_overlap_08a` checks active Event and static allocations; `deployment_allocate` and `site_shift_allocate` lock the exact demand then `people` row before candidate/capacity checks. A 17C implementation should extend the same guarded candidate assessment with a private approved-time-away predicate and safe `APPROVED_TIME_AWAY_CONFLICT` reason, and recheck that predicate **after the same Person row lock inside each allocation transaction**, immediately before insert. A preview is advisory; a stale candidate result cannot authorise a write. No warning acknowledgement, role override or Availability declaration can bypass an approved leave hard block. Keep the existing Event/static overlap and capacity checks intact.

The 17B approval and final-cancellation operation should lock the exact request/revision and then the same Person row before changing effective leave state; reconcile the lock order with the allocation writers to avoid deadlocks (prefer source/request lock, then Person; never acquire another demand lock after Person). Its approved segments and decision commit atomically. Under the Person lock, query both typed active allocation sources for overlap, create durable idempotent issue/history rows bound to request/segment decision revision, exact allocation ID, Person and duty-source revision, and commit them with approval. A repeated request key returns the same result; a stale expected request revision conflicts. If the allocation wins the Person lock first, it may commit and the following approval records its conflict. If approval wins, the following allocation sees approved leave and fails. No interleaving may leave an active newly allocated duty and an approved overlap without either a rejected new allocation or a recorded reconciliation issue. Use a database isolation/read strategy that observes the winner after the lock; verify this race explicitly, rather than assuming a pre-lock snapshot is fresh.

Staff acceptance from `ALLOCATED` to `ACCEPTED` should also recheck approved leave in its guarded transaction under the Person lock, with a consistent lock order and expected allocation revision. If leave was approved after allocation, acceptance is denied with the safe conflict reason until an authorised operational reconciliation. Staff decline and authorised cancellation remain possible; a leave block must not trap resolution. Other Event/static paths that create, reactivate, move or retime active duty must use the same guard or reject the transition; audit actual writers before implementation. No direct table write or alternate RPC may bypass it. Already `ACCEPTED` duties retain their response and receive `REVIEW_REQUIRED`, not automatic reversal.

An issue records its cause and source snapshots without copying leave category, narrative or private evidence into scheduling tables. Resolution is explicit and attributable. The operational manager uses existing guarded allocation authority to cancel or reassign a duty where permitted, then explicitly closes the issue after reviewing the current source state. A Time Away manager may cancel leave only through accepted 17B authority and receives no allocation authority. An operational manager receives no leave edit or cancellation authority. Final leave cancellation or allocation cancellation leaves the issue open until operational closure; no manager may close it as an accepted overlapping duty. There is no override in 17C. Demand gaps remain demand minus active allocations, not the count of leave issues.

## Scope, security and presentation

Candidates and operational Workforce rows may show only `BLOCKED` and the factual safe code `APPROVED_TIME_AWAY_CONFLICT` for an authorised Person/duty pair. Do not expose leave type, reason, notes, request ID, other days, medical information or another team's totals. The scheduling role gains no generic Time Away read permission. Staff sees their own exact request and associated duty conflict through existing self scope; a leave manager sees protected request details only through 17B's exact finite team/action grant. An operational manager sees the exact allocation and a safe conflict indicator through existing Event or Site Service scope. Every row, total, search and export reauthorises both Person and typed source path on the server. RLS denies ordinary direct table writes/reads to private segments and reconciliation history; security-definer functions use fixed search path, narrow grants and authenticated actor resolution. Forged Person, source, revision or issue IDs fail without revealing private leave existence.

Show the conflict on candidate cards, exact allocation detail and Workforce conflict views, distinguished from `DECLARED_UNAVAILABLE` and recorded allocation clash. Approval over an active duty shows the manager an explicit conflict count and exact authorised allocation links before decision, but does not require the scheduler to inspect leave category. Staff and manager flows fit desktop and 390px, keyboard/focus use, readable local date plus time-zone context for overnight/DST, no horizontal overflow and the accepted no-green visual rule. A stale preview must show a reload/conflict state after transactional rejection, never a success-looking local save.
