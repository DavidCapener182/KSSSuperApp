# TASK-06A proposal — Client, Site/Venue and Event foundation

**Status:** approved by David on 23 September 2026 and implemented in the synthetic development environment. See `TASK-06A-REPORT.md` for actual changes, verification and remaining gates. Staging and deployment remain untouched.

## Outcome and boundaries

Connect the accepted commercial and operational identities as **CRM Organisation in a Client relationship → existing Site/Venue → dated Event**. Keep `crm_organisations.id` as the one Client identity, `sites.id` as the existing location identity, and a new stable Event UUID. A static Site may have no Events. A Won Opportunity creates neither a Site nor an Event automatically. The later 06B/06C tasks own Staffing Requirements and Deployment; 06A contains no staffing quantities, shifts, pay/charge rates, timesheets, invoices, recurrence engine, document library or staff eligibility rule.

This design uses only synthetic development data. Existing Sites, SiteAssignments, onboarding Site context, URLs, private documents, People and CRM pipeline remain intact. The master roadmap remains authoritative; this is one bounded Phase 06 slice.

## Inspection finding that controls the design

Today, `sites` has stable UUID, immutable reference/creator, address/reporting point and `DRAFT → ACTIVE → RETIRED` status. Its RLS lets Super Admin read all, Office read/manage only creator-owned Sites, and Security Staff read an active assigned Site. Operations has no `SITES_VIEW`. The onboarding start path calls `private.office_owns_site`; SiteAssignment is a separate staff-to-location grant. CRM Organisation/Contact/Opportunity rows are Office/Super only. Therefore a new Client link must not be interpreted as a grant to CRM, onboarding, Profile or Document records; and Operations cannot be given raw CRM table access for Event display.

## Commercial Client and Site link

- `crm_organisations.relationship_status = CLIENT` is the current Client identity. No new Client master or copied company/contact/history rows. A separate Client-service profile is **not needed in 06A**: there is no approved operational-only field yet that warrants one.
- Add a narrow typed `site_client_links` record with one current Client Organisation per Site (`site_id` unique, `organisation_id` FK), linked actor/time and immutable linkage event/history. This keeps new commercial IDs out of the currently broad `sites` row returned to assigned Staff. It also avoids changing existing Site columns/UUIDs and permits every existing unlinked Site to remain valid. The Site's controlled `site_type` may be a new nullable column on `sites`, defaulting to `STATIC_SITE` only for **new** explicitly classified Sites; existing Site types remain `UNCLASSIFIED`/null until an authorised user classifies them. Proposed values: `STADIUM`, `VENUE`, `RETAIL`, `WAREHOUSE`, `OFFICE`, `FESTIVAL_SITE`, `STATIC_SITE`, `OTHER`.
- A new link requires current `CLIENT` status and an active authorised Office/Super actor who can manage that Site under its **existing** creator rule. Link an existing unlinked Site only by explicit choice after viewing both exact records; never infer an owner from names or addresses. Client status is checked at link/create time. A later relationship change does not erase historical Site/Event links; handling a Former Client with live operations requires a separately approved business rule.
- To avoid ambiguous Event provenance, 06A permits a Site's initial Client link but **does not permit replacing/removing it once Events exist**. A wrong link discovered after an Event is created stops for a future controlled correction workflow; it is not silently overwritten. Before Events exist, a correction may be a guarded operation with reason and typed old/new history if the implementation can preserve existing Site/onboarding authority. No automatic relink or deletion.
- An optional primary operational Contact references an existing active `crm_contacts` row of the linked Organisation. Store this on the link (or a narrow related field) only if implementation shows a useful Site workflow; otherwise keep the Event primary Contact only. The database enforces same-Organisation membership, including after Contact updates/deactivation. No duplicate Site Contact record.
- Keep existing Site `DRAFT → ACTIVE → RETIRED` lifecycle and creator/assignment rules. Client status and Site status are different. New Client-linked Site creation uses the accepted Site creation flow plus an explicit guarded link; a partially created Draft Site can remain safely unlinked if linkage fails, with truthful UI feedback.

## Event model

Create `events` with: UUID, `organisation_id` FK to Client Organisation, `site_id` FK to existing Site, optional `primary_contact_id` (same Organisation), optional `source_opportunity_id` (same Organisation, exact `WON`), controlled `event_type`, bounded name, `starts_at`/`ends_at` as `timestamptz`, explicit `status`, `owner_person_id`, creator and database timestamps. Site and Organisation are required in 06A: this is a **venue-based Event** slice. This does not force static Sites to have Events. A future mobile/multi-venue operation may need an approved extension instead of a fake Site. Initial types: `FOOTBALL_MATCH`, `FESTIVAL`, `CONCERT`, `PARADE`, `CONFERENCE`, `CORPORATE_EVENT`, `OTHER`.

The Event's Organisation must equal the Site's exact active link. The Contact must belong to that Organisation. The optional Opportunity must belong to that Organisation and be `WON` at Event creation; the link is provenance, never Event authority or automatic operational approval. One Won Opportunity may link to many Events. An existing Client can create an Event without any Opportunity. New Event creation requires an `ACTIVE` Site and current `CLIENT` Organisation. A later Site retirement or Client-status change retains the Event history and triggers a visible operational warning, not deletion or a silent status mutation.

Store timestamps in UTC, display/enter in Europe/London, and reject ambiguous or nonexistent local DST times. Require `ends_at > starts_at` (rather than equal); cap implausibly long intervals with a conservative documented limit or require an explicit long-event confirmation. No automatic lifecycle transition based on clock time. A multi-day festival is one Event interval; individual football fixtures are distinct Events.

Initial state `PLANNING`. Allowed normal transitions: `PLANNING → CONFIRMED`, `CONFIRMED → LIVE`, `LIVE → COMPLETED`; `PLANNING`, `CONFIRMED` or `LIVE` may become `CANCELLED` with reason. Do not allow terminal reopen in 06A. `CONFIRMED` is an Office/Operations planning state, not a signed contract, staffing approval or readiness verdict. `LIVE` is an explicit operator action, not inferred from the start time. Record actor, old/new state, reason where required and database time in immutable typed Event history. Event owner/date changes also create typed history; after `CONFIRMED`, date changes require a reason; after terminal state, key Event fields are immutable absent a future correction workflow. No destructive delete control.

The Event owner is an active Office Admin or Operations Person. Ownership means accountability, not exclusive Event visibility. Owner changes require reason and history. A role-expired owner remains in history; an active Office/Super user can explicitly reassign the Event. Event ownership grants no CRM, People or document access.

## Access and projections

| Actor | Client/Site/Event behaviour in 06A |
| --- | --- |
| Super Admin | All operational records, attributable oversight; existing private source policies still apply. |
| Office Admin | Existing CRM access; may create/operate Events and link Client to a Site they can **already manage**. Office Site creator ownership remains the rule for Site editing and SiteAssignment. Event viewing may be organisation-wide operationally, but does not confer edit rights on another person's Site. |
| Operations | Safe operational Client/Site/Event projection and guarded Event planning/status/date/owner actions. No CRM workspace, Opportunity pipeline, Contact email/phone, SiteAssignment administration, Profile, onboarding or private evidence. Event mutation is limited to approved operational fields and an active role; no Client link or Site creator change. |
| Security Staff | Existing assigned-Site access unchanged. No Events workspace, Client relationship browser or Event administration in 06A. Later Deployment/briefing will define assigned Event read. |

Provide explicit guarded read projections for Operations: Client display name/trading label and identifier for exact linked operational records; Site name/reference/type/address/reporting point/status as required for operations; Event name/type/date/status/owner and primary Contact **name/job title only** where necessary. Do not expose Contact business email/phone, CRM notes, values, Opportunities, stage/history or pipeline counts. A source Opportunity link should be shown to Office/Super only; Operations gets no Opportunity ID or title. Staff receive no new linked-Organisation/Contact columns from raw Site reads. Prefer narrow guarded RPCs or security-invoker views with explicit columns and server checks; do not grant Operations select on `crm_organisations`, `crm_contacts` or `crm_opportunities`.

The new link/Event tables get RLS, minimum column grants and guards. All writes are exact guarded operations: actor from Auth mapping; action-specific role; Site/Organisation/Contact/Opportunity relationships checked in the transaction; old/new status and ownership locked as appropriate. Search, list, detail and count apply the same access predicate before pagination. Guessed IDs return no protected data. Existing Site RLS, `private.office_owns_site`, SiteAssignment, onboarding and CRM authority are **not** weakened for convenience. If the intended Office or Operations journey cannot work without a material change to those policies, implementation must stop and return the exact conflict for approval.

## UI and routes

- Existing `/sites` and `/api/sites` stay valid. Evolve the Office Site/Venue workspace with Client context where linked, type/status, search by Site/Client and a detail view showing authorised Client, primary operational Contact if used, upcoming Events and existing authorised SiteAssignments. Operations receives an operational read view without being admitted to the current creator-only Site administration actions. Staff see their same assigned-Site journey.
- Add `/events` and `/events/[id]` with Upcoming, Planning, Live, Completed and Cancelled views; date range, Client, Site, type, status and owner filters; server-authorised counts and pagination. Calendar is deferred. Detail shows Client, Site, local start/end, status, owner, permitted Contact, optional Office-only Won Opportunity provenance and curated typed history. Staffing Requirements, Deployment and Briefing/Documents are labelled unavailable/not built; no fake records.
- CRM Organisation detail gets real linked Sites/Events sections for Office/Super, replacing the relevant placeholders. The deep link to a Site or Event re-authorises independently. A guarded **Create operational Event** action can prefill Organisation and eligible Site from a Won Opportunity, but requires Office confirmation and never runs on the Won transition itself.
- Desktop uses concise operational tables and detail columns; 390px uses cards, comfortable controls and no horizontal page overflow. Follow the accepted shadcn/iOS-inspired blue/graphite/neutral tokens with **no green**. Status always includes text. Loading, restricted, empty and conflict states are truthful.

## Schema, audit and migration approach

Proposed minimum additive objects: `site_client_links`, optional `sites.site_type`, `events`, immutable `site_client_link_events` and `event_events` (or equally narrow typed histories), composite relational constraints/indexes, guarded read/write operations, RLS, and audit entity-type additions. No Client master/profile table, recurrence table, staffing table or generic workflow engine. Prefer typed history as the authoritative business record; `audit_events` gets actor/IDs/action/changed-field names and timestamps without copying Contact values, detailed address or Event notes. No raw audit JSON in UI.

Implement a forward migration that leaves existing Sites unlinked and preserves every UUID, assignment and onboarding reference. Before applying it, read back the current Dev schema and policy definitions and validate that new guards preserve `private.office_owns_site` semantics. No automatic name-based backfill. Develop against the dedicated synthetic Dev project; no staging migration or deploy. Seed only the explicit Northshore demonstration through guarded application operations, not by bypassing business history.
