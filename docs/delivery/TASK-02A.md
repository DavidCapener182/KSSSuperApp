## Outcome and boundary

Prove one synthetic personnel-document evidence journey: an authorised Office Admin creates a request for one synthetic Security Staff Person; that Person sees it and uploads one synthetic file; the system records a submitted version; the requesting Office Admin can retrieve its bytes; another staff member and Operations cannot discover its metadata or retrieve its bytes. Super Admin retains audited review access. This is the first Phase 02 vertical slice, not a complete document-management system.

Relevant references: Phase 02 prompt (R04, R15, R25, R27), master R04/R05 and controlled-document appendix, accepted Person/AuthIdentity separation, 01C Site scope, 01D capability routing. Preserve `Requested ≠ Uploaded ≠ Submitted ≠ Verified/Approved`. An upload accepted by Storage is not a verified document, valid credential, eligibility finding or completed onboarding check.

No SharePoint import/integration, existing KSS files, Trello-style tasks, general approvals, document explorer, acknowledgements, publication, review/rejection, verification, Entra, live identities, production/Vercel deployment or next task is included. Do not add a Site-assignment administration UI.

## Proposed minimal model

| Record | Purpose and minimum fields | Authority/lifecycle |
|---|---|---|
| `document_requests` | UUID, target `person_id`, requesting `office_person_id`, **optional** `site_id` as creation context, short controlled `kind/title`, `status`, timestamps. The site link is context for this proof, never a universal requirement or file audience. | `REQUESTED` when Office creates it; `SUBMITTED` only after verified server receipt of a Storage object and committed version. No `VERIFIED`/`APPROVED` state in 02A. |
| `documents` | Stable UUID, request ID (unique for this slice), owner Person ID, fixed initial `PERSONNEL_PRIVATE` classification, `source_kind=ENTERPRISE_NATIVE`, creator and timestamps. This is the logical document; it is not the object path. | Created with its request. Audience is resolved explicitly from request/role policy, never inherited from Site or future linked records. Leave room for a later external-source mapping without changing the Person or Document ID. |
| `document_versions` | Immutable UUID, document ID, version number, random server-generated object key, original filename as bounded display metadata, detected MIME, byte size, SHA-256 hash, uploader Person ID, `upload_state`, `scan_state`, timestamps and an idempotency token/hash. | One version may be submitted in 02A. `PENDING_UPLOAD`/`UPLOADED_PENDING_COMMIT` are internal, not shown as submitted; `SUBMITTED` follows successful storage receipt and metadata commit. A future replacement gets a new row/object, never an upsert or overwrite. |

Reuse and minimally extend the existing `audit_events` infrastructure for request creation, submission/version finalisation and any privileged mutation. Do not create `document_events` without a separate user-facing timeline requirement and David's further review. Keep audit payloads limited to IDs, state and actor; never include bytes, secrets or unnecessary filenames.

Use UUID foreign keys to the existing stable `people.id`; never identify an employee by Supabase Auth user ID. Define `status`/`upload_state` checks and legal transitions in database constraints or guarded functions as well as server code. Constrain one submitted version per request in this slice and unique `(document_id, version_number)` plus unique idempotency token per request/uploader. Avoid storing raw browser filenames or file bytes in audit JSON. A document may later have more versions and more restrictive classifications without changing its identity or widening its audience. The implementation brief may refine field names after schema review, but must preserve these relationships and invariants.

## Authorisation decision for this slice

- **Office Admin:** may request evidence only for a Security Staff Person with an active role and an active assignment to a Site the Office Admin created and may manage at request creation. Use a scoped target picker/read endpoint; no unrestricted People search. The creating Office Admin may see the request and submission while their Office role remains active. Office B cannot see Office A's request merely because it is Office Admin or manages another Site. If later access ownership changes, define that explicitly in a later task rather than inheriting Site access.
- **Security Staff:** may read requests and submitted versions addressed to their own stable Person ID and upload/submit only against their own `REQUESTED` request. Their active Security Staff role is required on every request. Site assignment establishes eligibility at request creation; a personal request does not silently become a Site-wide document. Staff B cannot list/search/count/detail/download Staff A's request or object.
- **Operations:** no request, document, version or file access in 02A, even when Operations is one of several active roles unless another role independently grants the precise action.
- **Super Admin:** may read/review all synthetic requests and create requests for an active synthetic Security Staff Person; privileged creation/retrieval is attributed to the actual Person and audited. No general document administration UI is proposed.
- **Anonymous, unmapped, expired-role users:** no document access. The server resolves the current AuthIdentity→Person and current role assignments for every API/page action; user metadata and hidden links do not authorise access.

Add narrow `DOCUMENT_REQUEST_CREATE`, `DOCUMENT_SELF_READ`, `DOCUMENT_SELF_SUBMIT`, `DOCUMENT_OFFICE_REVIEW` capabilities to the existing server-owned map only as implemented, and use the same checks for navigation and route gates. Record-specific policy then narrows them by target/creator/site context. RLS independently enforces the equivalent database audience. Future classifications must be an additional restrictive gate (`allowed role/action ∩ classification ∩ explicit audience`), never a union of all linked records' viewers. In particular, linking a personnel file to a Site must not make it visible to Site viewers.

## Private Storage and upload protocol

Propose one new **private** bucket, `enterprise-personnel-evidence`, with a 5 MiB bucket limit and allowlist `application/pdf`, `image/png`, `image/jpeg`. 5 MiB stays within Supabase's currently documented standard-upload recommendation for small files. Apply the same limit and allowlist at the server. Exact project limits must be checked before implementation. No public bucket, permanent public URL, bucket listing permission or browser service-role/secret credential.

Use a server-generated object key such as `<random document UUID>/<random version UUID>`; no name, email, employee number, request title, original filename or predictable Person ID in the key. Retain a Unicode-normalised, control-character-stripped, bounded original filename for display and safe `Content-Disposition` only. Reject traversal/separator tricks. The object key is not an access token.

The browser sends the small file to a Next.js server route with the ordinary authenticated session. The route limits request bytes, validates declared MIME and extension **against detected bytes** (PDF signature or image signature/decoder), computes size and SHA-256, and refuses mismatches/unsupported content. It then uploads using a **user-scoped Supabase client/publishable key**, so `storage.objects` RLS still applies; `upsert=false` and no Storage UPDATE or broad SELECT policy. The route may stream/buffer up to the bounded limit after verifying the runtime's behaviour. Do not infer that allowed extension, MIME or magic bytes proves malware safety. In 02A use synthetic files only, `scan_state=NOT_SCANNED`, no inline rendering and attachment download with `nosniff`. Malware scanning availability, vendor, retention and policy for real evidence remain open gates for a later task and live pilot.

The server creates/locks a `PENDING_UPLOAD` version and stable attempt ID before Storage upload; a browser value is not trusted as identity or authority. Mark it and its request `SUBMITTED` only after successful Storage receipt and metadata transaction. Store an immutable hash/size/object key; never overwrite an accepted object. A retry of the same authorised attempt resumes/reconciles it; another attempt after a submitted version receives a conflict. If Storage succeeds but final database commit fails, retry checks the expected object key/hash before finalising. Failed uploads remain visibly unsubmitted. Provide a bounded dry-run-capable development cleanup command for synthetic stale pending attempts/objects (for example, older than 24 hours), never deleting submitted versions, unknown objects or audit history. No unattended production scheduler.

All retrieval goes through a server document/version route that checks record access again, then downloads by private bucket/object key with the user-scoped client. Return `Cache-Control: private, no-store`, attachment disposition and safe error text. Storage RLS must independently allow authenticated object download **only** when the caller can read the matching submitted `document_versions`/`documents`/`document_requests` record. Use operation-aware Storage policy if needed to allow download without list. Exact path guessing, direct authenticated Storage API calls, and copied object URLs must obey the same policy. Do not issue signed URLs in this slice; if implementation needs them, revise the brief with expiry/revocation and audit limits before use.

## Minimal UI and routes

- Office/Super Admin: a small Documents view with permitted target selection, request creation and own/authorised request detail; show `Requested` or `Submitted (not reviewed)` and a protected download action.
- Security Staff: a Documents entry from My Work, own request list/detail, one-file upload and explicit Submit result. A file selected in the browser is **not** submitted; failed upload is shown as failed/pending with retry.
- No Documents link for Operations, anonymous or unmapped users. No full explorer, folders, SharePoint clone, search across all People, approval button, verification badge or fake onboarding completion.

The exact route names can be set during implementation; proposal: `/documents` and `/documents/[requestId]` with server-gated page/API routes. Avoid putting object paths in page URLs. Keep the existing shell and Site journey intact.

## Acceptance tests and demonstration

1. Office A signs in, sees only eligible synthetic Staff targets and creates one request for Staff A at Site A. Office B cannot create/read a request for Staff A through a forged target Person/Site ID.
2. Staff A sees that request and its `REQUESTED` state; Staff B's list, search, count, direct request/document/version IDs and metadata are empty/denied. Anonymous, unmapped and Operations users receive no request metadata or file bytes.
3. Staff A uploads one allowed **synthetic** file. Invalid size, extension/MIME mismatch, forged target, altered object key, duplicate token, concurrent replay and interrupted upload have defined outcomes. Upload success without final commit is not shown as submitted. Same-token retry does not create a second submitted version.
4. After final commit, request and immutable version read as `SUBMITTED` and `NOT_SCANNED`, never `VERIFIED`/`APPROVED`. Audit identifies the Office requester and Staff uploader without file contents.
5. Office A downloads the exact uploaded bytes and SHA-256 matches the synthetic fixture. Staff A's authorised own download is checked. Staff B and Operations fail to retrieve **bytes** through the application route, direct private Storage request, guessed/swapped object path and copied URL. Unauthorised failures do not leak filename, hash or document existence.
6. Role expiry/revocation removes page, API, database and Storage access on the next request. A Site link does not broaden access. Database RLS tests use ordinary authenticated clients; server tests exercise the route gate independently.
7. Desktop Office request/retrieval and 390px Staff request/upload/retry are demonstrated in the browser, including focus/labels, no horizontal overflow and honest pending/error/success states. Run clean install, lint, webpack build, smoke, 01B/01C/01D regressions, new document/RLS/Storage tests, migration readback, bucket privacy check, staged secret scan and targeted independent Sol security review. Record any environmental interruptions separately from product failures.
