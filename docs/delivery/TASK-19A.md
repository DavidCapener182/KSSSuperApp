## Assignment contract

Create an operational assignment as its own stable business record referring to **one exact `controlled_document_versions.id`** and its parent document. Keep the version's hash, object key, PDF and publication history at the source; assignment rows contain references and policy metadata, never copied bytes or permissive signed URLs. The record carries target kind and ID, `effective_from` and exclusive `effective_until` (optional), `acknowledgement_required`, creator Person/time, reason, state and revision. Target kind is exactly one of `SITE`, `SITE_SERVICE`, `EVENT`, `OPERATIONAL_ROLE`, `PERSON`. `OPERATIONAL_ROLE` uses the existing `operational_role_definitions.id` plus a required exact Site, Service or Event context ID; it is never an arbitrary role string or Auth role. `PERSON` uses stable `people.id`, independent of Auth identity. Validate target existence and typed membership transactionally: Service belongs to its Site and Client link; Event belongs to its authoritative Site/Client context; a broad Site target must not be inferred from a Service or Event target. Duplicate active target/document/version/date windows should conflict, while historical windows remain intact. Disallow retroactive edits to an effective interval once it has exposed a document; close/revoke and create a new assignment instead.

Operational target resolution is a **bounded projection**, not an audience grant. A named Person assignment addresses that Person only. Role targeting resolves to people holding the matching operational role within the relevant actual work context; a role definition alone does not expose a document to every holder across KSS. Site, Service and Event targets resolve only to people currently assigned to that exact context under the accepted workforce/allocation contract, including date overlap. Availability alone never qualifies; a staffing plan or unaccepted allocation is not an assignment. Exact active/future qualifying static allocations under Site Services can resolve Service/role audiences. Past work at a Service does not grant ongoing access. If no current/future Person relationship is provable, the Service assignment remains manager-side configuration and exposes no PDF to Staff. Do not invent permanent Service membership. Do not infer a person audience by traversing Client or Site links. A person who loses a context assignment loses current file access immediately, while their historical acknowledgement remains visible to authorised managers.

Require a published, ready controlled version with effective date reached before assignment becomes actionable. A scheduled future version may be staged but cannot be opened by Staff early. `ACTIVE`, `SCHEDULED`, `REVOKED`, `EXPIRED` and `REPLACED` are factual assignment states derived from explicit events plus dates, not document compliance states. Store append-only assignment events for creation, effective-date change before exposure, revocation and replacement, with actor, timestamp, reason and exact old/new IDs. No deletion of exposed history. Version state and assignment state are separate: a superseded version is retained for historic readback, but new open requests should point to a deliberate replacement.

**Replacement:** publishing v2 never silently rewrites v1 assignments or acknowledgements. The current 03C unresolved-assignment supersession guard must remain valid for onboarding; operational publication needs a separate guarded replacement transaction/policy. An authorised manager previews affected active audiences, sets a v2 effective time, and explicitly chooses replacement of each applicable v1 assignment. The transaction closes v1 intervals and creates new v2 assignment IDs with provenance to the prior assignment. If acknowledgement is required, each resolved recipient gets a fresh exact-v2 request; prior v1 acknowledgement remains immutable and labelled historical. Partial replacement and exceptions are visible, and an unresolved required request is never silently treated as complete. Revocation or expiry closes outstanding requests without generating a completion event. No clock job may automatically attest to a new version.

## Reading and acknowledgement

Staff **My Documents / Required reading** lists only current actionable exact-version assignments resolved for the signed-in Person; show context, title, version, effective date, required/optional label and factual `Not opened`, `Opened`, `Acknowledged`, `Replaced` or `No longer assigned` status. For one document reachable by several targets, preserve every underlying assignment but present one current version card with its contexts and one explicit acknowledgement action; bind the acknowledgement to the exact request/version and recipient, with a unique key to prevent double credit. If conflicting versions are simultaneously current for one Person/document, block the card as a configuration conflict for manager resolution; do not select a version by timestamp. Staff can open an authorised PDF through the existing private route only after actor, exact assignment, target resolution, date, version and source file policy are rechecked. Record an open request before bytes are served, as in 03C; it proves neither delivery nor reading. An affirmative Staff action records an immutable exact-version acknowledgement with actor Person and server timestamp. Manager status shows numerator/denominator for resolved required recipients, unacknowledged people and historical versions, with an as-of timestamp and scope explanation; it says **acknowledged**, never trained, qualified, compliant or safe to deploy.

The source controlled-document permission remains authoritative on metadata, list, search, export and bytes. Operational assignment may supply an explicit narrow audience to the operational family only; it must not widen `document_versions` personnel evidence or `ONBOARDING_TERMS_SYNTHETIC`. A broad Site link, Mobilisation link, manager access to Site, or guessed version ID grants nothing by itself. Publisher, assigner and reader authority are separately checked server-side and in database RLS/Storage policy. Start with Super Admin oversight and explicitly granted, time-bounded Office publisher/assigner authority; Operations view or assignment authority needs a named decision. Managers see only acknowledgement facts for authorised operational contexts, never unrelated private files. Audit access to private bytes and privileged publication/assignment changes without placing titles, content or personal data in broad logs. No public object URLs.
