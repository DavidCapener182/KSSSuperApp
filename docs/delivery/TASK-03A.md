## 1. Outcome and pilot boundary

Build the smallest visible onboarding journey for one **existing synthetic** `SECURITY_STAFF` Person. An authorised Office Admin starts a case against a versioned, company/role checklist for an explicitly synthetic generic static-security Site. Staff sees six requirements and a clear next action. One Right to Work (RTW) requirement follows the already protected document request, version, evidence review and Office Task flow; a **separate authorised requirement-verification decision** changes that checklist item to Verified. Accepted document evidence alone leaves it unverified. Core KSS induction remains outstanding with provider `NOT_CONNECTED`, so the case never becomes automatically complete or deployable in this proof.

Use the dedicated development project `dnfhkmmnlbiabqypclqg`, synthetic identities and synthetic files only. At implementation preflight, create or select a clearly named synthetic generic static-security Site through existing authorised Site controls; do not use Music Magpie, Blackpool FC, Footasylum or another real client. The Site identifies intended placement/context; it never widens a private onboarding or document audience. Use an existing synthetic Person such as Staff A for the first proof. Creating a new Person and binding a new authentication account is outside 03A unless separately approved.

This proposal develops the Phase 03A create-starter/checklist slice and one evidence-to-verification seam. It does not deliver full RTW legal checking, all six fulfilment flows, LMS integration, e-signature, SIA register lookup, eligibility, staffing assignment or recruitment. The Phase 03 map's broader 03B–03D work remains separately scoped. The product must label incomplete mechanisms honestly instead of manufacturing six completions.

**Permanent invariants:** `Person ≠ AuthIdentity`; `Task state ≠ business state`; `Evidence accepted ≠ requirement verified ≠ employee compliant ≠ eligible for deployment`. Onboarding completion, when designed later, remains distinct from operational eligibility.

## 3. Proposed minimum model and history

Prepare additive, source-controlled schema only **after** approval and implementation preflight. The proposal's logical records are:

| Record | Minimum purpose |
|---|---|
| `onboarding_templates` | Stable `SECURITY_STAFF` company/role template identity; optional synthetic Site context is recorded on the case, not a client-specific overlay. |
| `onboarding_template_versions` | Immutable published version number, effective/published timestamp, creator and controlled definition set. Draft edits produce a **new** version before future cases use them. |
| `onboarding_requirement_definitions` | Version-bound ordered requirement code, wording, mandatory flag, fulfilment kind, proposed owner/verifier role and provider state. Published definitions are immutable. |
| `onboarding_cases` | Stable UUID, stable `people.id`, intended role, synthetic `site_id`, exact template version, original Office creator/owner Person IDs, lifecycle and timestamps. A Person may have multiple historical cases across rehire, role or Site changes; no Supabase Auth ID is an employee key. |
| `onboarding_case_requirements` | One immutable instance per template definition per case; preserves the starting snapshot/version and current action owner. An RTW instance may link to one existing protected `DocumentRequest`; document versions remain in the Document service. |
| `onboarding_requirement_verifications` | Immutable business decision for an exact requirement instance: verifier Person, decision, decided time, exact accepted evidence version when applicable, optional synthetic validity end and controlled reason/comment when rejected or revoked. Audit is a separate ledger. |

The physical schema should be the minimum that meets these contracts; do not add a general HR profile, opaque JSON checklist as the sole source of truth, or six hard-coded UI booleans. Published template definitions and instantiated requirements are historical records. A new template version applies only to **future** cases; an existing case remains pinned to its original version and instances. A later migration of an in-progress case would require a separately authorised, attributable action rather than silent rewrite.

For 03A, propose case lifecycle `DRAFT`, `IN_PROGRESS`, `CANCELLED`. Starting the case instantiates the checklist once and enters `IN_PROGRESS`; cancellation retains history and stops actions. `READY_FOR_FINAL_REVIEW` and `COMPLETE` should wait for a defined final-review/eligibility policy, especially while induction and acknowledgement mechanisms are unavailable. Never infer deployability from case state.

## 4. Requirement state and verification contract

Persist authoritative facts: case lifecycle, immutable instantiated definitions, explicit action owner, the protected document request link, case response where approved, provider connection status, and immutable requirement-verification decisions. Derive display state from those facts and the current exact DocumentRequest/Version/Review:

- `NOT_STARTED`: no issued action or evidence link.
- `AWAITING_EVIDENCE`: an authorised request exists and Staff needs to respond.
- `UNDER_REVIEW`: evidence is submitted or accepted as evidence, but the required review or separate verification has not completed. The UI should say which decision is outstanding.
- `ACTION_REQUIRED`: the exact evidence was rejected, with the existing authorised feedback visible to Staff.
- `VERIFIED`: an authorised requirement-verification decision exists, refers to the exact accepted evidence version when evidence is required, and remains valid under an approved rule.
- `EXPIRED`: a previously verified requirement's **synthetic verification validity** ended; the old decision stays in history and the requirement no longer counts complete. The Document service currently has no general document-expiry model, so 03A must not claim a file expired merely from age.
- `NOT_CONNECTED` or `NOT_AVAILABLE`: a required fulfilment provider/action is unavailable, such as induction or controlled acknowledgement. It remains a blocker, not a completion.

Do not persist redundant `REQUESTED`, `UNDER_REVIEW` or `VERIFIED` flags that can disagree with their source records. Do not introduce `BLOCKED` as an editable catch-all; show explicit blockers derived from missing evidence, unavailable provider, expired verification or missing Office decision. If an explicit hold becomes necessary, design its reason, owner and audit in a later task. The responsible actor (`STAFF`, `OFFICE`, `EXTERNAL_PROVIDER`, `SYSTEM`, or `NONE`) is workflow routing, **never** an access-control shortcut.

The RTW proof sequence is: Office creates the case and targeted protected request → Staff submits a synthetic Version 1 → document review Task appears for the original Office requester → Office accepts that exact version **as evidence** → document Task becomes Done → RTW remains `UNDER_REVIEW` / “Office verification needed” → authorised Office case owner makes a separate verification decision referencing the requirement and accepted Version 1 → RTW becomes `VERIFIED`. If the document is rejected, Staff sees action-required feedback and can submit Version 2 through the existing replacement flow; a verification decision must bind Version 2, never silently transfer from Version 1. If a later version or validity change makes a prior decision stale, retain the old decision and show re-verification needed. No Task state change can forge this decision.

Initial verifier authority is the original authorised `OFFICE_ADMIN` case owner, with audited `SUPER_ADMIN` oversight/override. Staff cannot verify self. Office B cannot verify or read another Office's case by guessing IDs or by sharing a Site assignment. The verifier must have independent authority to read the linked exact document and review; a case link never grants file access. Verification requires an accepted exact version for the RTW proof, checks target Person/request/case/requirement binding, and records a reason/comment for rejection or reversal if those actions are approved. No Office user can enter a legal RTW expiry, status or document combination without separately approved KSS/legal configuration; a synthetic validity date may be used solely to test expiry mechanics and must be labelled as synthetic.

Operations receives no private case, evidence, response or verification route in 03A; a later eligibility outcome can have its own narrow audience.

**Tasks:** reuse the existing `DOCUMENT_REVIEW` Task automatically created by the RTW document submission. Its Done state follows the evidence decision and does **not** complete the RTW requirement. In 03A, show “Office verification needed” as a case work item in the onboarding workspace, without creating a second Task type, Staff Task, team queue or reminder. A future `ONBOARDING_REQUIREMENT_VERIFICATION` adapter would need an approved source/assignee model, creation/completion event, RLS, exact navigation and negative tests. Task ownership never grants onboarding or document authority.

## 6. Access, audit and integrity proposal

Use server action + record checks and PostgreSQL RLS for cases, instances, responses and verifications. Staff sees only their own case and appropriate feedback. Office sees only cases it owns under an active role and may act only on its own authorised source; Site assignment alone does not enlarge the audience. Super Admin may perform explicitly audited oversight. Anonymous, unmapped, Staff B and Operations receive no protected case metadata or bytes. Document APIs and private Storage keep their independent audience checks. No privileged key reaches browser code.

Ordinary clients must not directly insert a verified decision, alter case Person/template/source links, backdate validity, mutate published definitions, write onboarding audit events or mark a case complete. Guarded server/database operations bind the verification to the correct instance, case target, document request, exact submitted/accepted version and authorised verifier. Audit creation, version instantiation, response/link changes, verification and cancellation with Person IDs and controlled metadata, never file contents, identity evidence, full personal responses or secrets. Verification remains a business row even if audit is unavailable; decide transaction coupling during implementation design, and never report a verification success if its required audit or Task event fails.
