# TASK-13A proposal — Operational Control Room

**Status:** Accepted by David in synthetic Dev on 24 September 2026 at implementation commit `975f432`; see `TASK-13A-REPORT.md`. No staging, production, live data or deployment authority.

## Purpose and boundary

David's implementation decisions: active Operations, Office Admin and Super Admin use the existing accepted Event/Site operational authority; Security Staff keep self-service only. The default windows are current Live/today, upcoming 14 days and recent seven days. Refresh every 60 seconds with manual Refresh and visible snapshot time. Large display is summary-only and omits Staff names. Include Incidents only when the user separately has 12A Incident Reviewer authority; omit the module entirely otherwise. Include a safe 08D operational health projection with no private run internals. Omit manager action counts in this first slice. Source modules retain their permission rules; a single UI snapshot contract composes narrow projections and does not become an independent Enterprise permission engine. No writes, inferred no-show, worked time, or score.

Provide an Office/Operations/Super Admin daily read view over authoritative Event and static Site Service facts. The four areas are **Live Now**, **Upcoming**, **Needs Attention** and **Recent Operations**. Every number opens the exact authorised contributing records. The Control Room neither creates operational state nor makes a readiness, compliance or risk judgement. It does not infer no-shows, worked time, pay, billable hours, or a completion outcome from elapsed clock time.

The view composes persisted Event lifecycle, active staffing requirement/allocation/response, factual attendance, explicit availability conflict, Incident follow-up . Static equivalents use Site Service lifecycle, dated demand, static allocations, 08D horizon health, and accepted 09B static attendance. It never reads 10B work-time tables or depends on their unfinished schema. 14A handover may later link back to a source context; 13A owns no handover storage, state or write.

## Delivered contracts and source map

Use exact stable source IDs and current guarded projections as the starting contract, then confirm schema and acceptance at implementation time. `operational_events` has Planning, Confirmed, Live, Completed and Cancelled states (06A); `event_staffing_requirements` and `event_staff_allocations` supply active Event demand and response (06B/06C). `deployment_event_summary` gives required, allocated, accepted and remaining counts for one Event. `workforce_week_08a` already composes Event and static demand, returns line source, IDs, dates, staffing and conflict counts, and signals `static_horizon_covered`. Static identities are `site_services.id`, `site_shift_demands.id` and `site_shift_allocations.id`; active demand is a persisted PLANNED occurrence, not a generated expectation. `site_shift_maintenance_health_08d` has last run, last success, configured window and 36-hour overdue result, but currently has a narrower administrator guard. 09A Event attendance and 09B static attendance are factual case/event histories with exact source allocation FKs; 09B was accepted at `1e63979`; its desktop/390px visual check remains a follow-up. 12A Incidents have restricted reviewer authority and sensitive content; the Control Room must not reuse a broad operational role to reveal them. 08C Staff Action Centre notifications are recipient-only and cannot become a manager-wide action feed.

A “needs attention” label is a navigation grouping, not a finding.

## Identity, authority, privacy and history

The server derives the caller's current mapped Person and active roles per request. Active Office Admin, Operations and Super Admin receive the manager Control Room under the existing accepted Event/Site operational authority; each row and deep link still passes the destination guard. Do not add a new team/scope system: Event owner, Site owner, SiteAssignment, work-role title or possession of a UUID alone must not grant access. If current operational APIs are organisation-wide, preserve that only where it is the accepted contract and document it; do not silently widen Incidents, private Person, documents or attendance. Staff get their own existing My Work/My Deployments/My Attendance routes, not manager totals. Client access is excluded. Expired/unmapped/anonymous users receive no counts or existence oracle.

A Control Room Person chip may show only an authorised operational display name, exact allocation Person ID for guarded navigation, allocation response, and safe conflict label. No phone, email, DOB, address, credentials, SIA, medical, availability note, onboarding evidence, private file, incident narrative or work-time/pay data. If a manager cannot open the exact Person record, omit the link. No cross-source Person search, public cache, analytics payload or export. Linked files retain their own audience. No new mutable business table is proposed. Source histories remain append-only, with correction/revision attribution retained; Control Room snapshot metadata may be transient and must not overwrite facts. Corrected attendance displays the latest accepted factual projection plus a link to authorised exact history, rather than erasing the original.

## Read contract, consistency and freshness

Propose one bounded read-only `control_room_13a(window_from, window_until, filters, cursor, limit)` database RPC behind a server route, or equivalent narrowly guarded server composition if its transaction consistency can be proven. Execute as one consistent database snapshot. `as_of` is database time, with Europe/London display dates and half-open UTC instants for duty inclusion. The server validates the approved fixed window (current day through 14 days ahead, plus seven days recent), exact source/site/client/status filters, `limit` 1–50, and an opaque cursor containing snapshot position and deterministic `(time, source, record_id)` tie-breaker. Reject oversized windows, arbitrary offsets, free-text SQL search and unknown filter values. Return `as_of`, `window`, `filters`, source freshness, `has_more`, bounded rows and counts computed from the same filtered authorised source set. For pagination across concurrent writes, pin a short-lived snapshot token or make totals explicitly page-snapshot scoped and refresh on the next request; do not mix totals from one query with rows from another. No count-only function may reveal records outside row scope.

Return `unknown` or `unavailable` for failed/unfinished dependent feeds, not zero. Show “Updated at HH:mm” and a visible stale marker after the approved 60-second refresh interval; user-triggered refresh reauthorises and takes a new snapshot. Polling, if approved, must be modest, abort stale requests, pause in hidden tabs, and never mutate source or trigger 08D generation. If the source is unavailable, keep the last successful snapshot clearly timestamped and stale, with no current claim. Avoid caching privileged responses across users; use no-store on server and browser fetch. Count definitions and inclusion/exclusion rules must be accessible beside each card, with exact drill-through filters and a displayed “showing N of M” when pagination applies.

The RPC should be `STABLE`, fixed `search_path`, least-privilege `SECURITY DEFINER` only if existing RLS/RPC pattern requires it, explicitly revoked from public/anon, and recheck active Person/roles plus row-specific authority internally. Tables keep RLS and direct authenticated access restrictions. No dynamic SQL or caller-selected Person. Read access must not call 08D maintenance, mark notifications read, change incident access logs unless the accepted 12A read contract requires its attributable access audit, or create any new write path. If an Incident read requires an audit write, isolate it to the existing 12A audited detail path; omit Incident details from the read-only aggregate RPC and treat the queue count under its approved guard separately.

## UX and guarded navigation

Desktop: a concise time/context header, source/site/date filters, four areas with labelled Event and Site Service rows, reconciled counts, visible unknown/stale/horizon states and exact source links. 390px: one column, no horizontal overflow, filters in a labelled accessible disclosure, counts next to their unit, full text alternatives for icons, 44px touch targets and no colour-only distinctions. Large display: optional read-only dense layout with larger type and visible update time; no kiosk public mode or ambient disclosure. Use neutral/amber/red styles and text; **no green**. Preserve keyboard order, focus after refresh/filter changes, screen-reader live announcement for refresh status without announcing sensitive rows, semantic headings/table or list labels, and reduced-motion support.

Deep links route through existing guards: Event detail and staffing, Site Service/demand, manager attendance, Workforce filtered week, and restricted Incident detail/action. Preserve source type and exact UUID in the URL; never put Person details or narrative there. Reauthorise on every destination request, including stale links after role revocation or source cancellation. If a destination has no authorised exact filter today, leave that card unlinked or define its guarded route in the separately approved implementation; do not link to a broad list and imply it is the same records.
