## Purpose and boundary

Give Office an accountable register of KSS equipment and stock, Operations an expressly authorised issue/transfer/return workflow, Staff a private **My Equipment** view, and a limited Site/Event equipment view. Track who or what currently holds an item, where it was last recorded, when return is expected, and what happened to it. A custody discrepancy is a fact requiring investigation, not a finding of fault, misconduct or a deduction. An issued item is not proof that a person used it or was at a shift. Attendance and worked-time systems do not consume custody events as time evidence.

The synthetic proof uses an existing synthetic Site and Event, one individually tracked radio, restricted key/card and device, and sized uniform stock. Full radio kits remain deferred. Use synthetic records until a named live source and rules are approved.

## Approved data and lifecycle contract

The first slice uses stable asset_items UUIDs and immutable human references for radios, keys/cards, phones, laptops/tablets and bodycams. An optional serial is class-unique. Keys/cards are restricted. Uniform uses asset_stock by garment, size and KSS store, with exact issue IDs and append-only quantity movements. Consumables/accessories may later use quantity stock where individual custody is unnecessary. Kit definitions and exact component snapshots remain a future schema seam; there is no full kit workflow in this slice.

An asset has one exact current custodian: Person, Site, Site Service, Event or KSS store. Physical location is separately recorded where known. Custody, controlled condition (GOOD, SERVICEABLE, DAMAGED, UNSERVICEABLE or UNKNOWN), and exception/maintenance state are independent. Availability is derived. Thus an issued radio can be damaged, and a store-held radio can be in repair. Expected return is explicit, with no universal overdue period. A lost/damaged report records an operational fact without blame, HR conclusion or payroll consequence.

Office registers items and verified opening stock and can make reasoned adjustments. Operations issue, transfer, return and inspect only with a current explicit scope grant. Staff see own current equipment, acknowledge or dispute receipt and report damage/loss; they cannot self-issue. Super Admin grants/oversees without automatic custody. An issue creates a pending recipient acknowledgement. A return records observed condition and requires a separate attributable receiving acknowledgement. Repair completion stays quarantined until inspection restores availability. Lost items need reasoned recovery before return. Retirement preserves history. Asset and stock events are append-only business facts, with revision checks and idempotent request replay. No Task is created by a fault or return in this slice.

A key/card must follow store → authorised manager issue → Staff acknowledgement → return → receiving acknowledgement → store. No alarm codes, key cuts or access instructions belong in asset notes. Bodycam inventory never grants footage access. Site/Event context references are exact IDs and do not change custody automatically. The handover and mobilisation integrations remain read/reference seams.

## Guarded interfaces and privacy

Proposed read interfaces: Office filtered register/stock/overdue queues; scoped Operations issue/return queue; Staff self `my_equipment`; Site/Event minimal equipment projection; exact asset history subject to class and holder scope. Search/count/pagination must be scoped before aggregation, avoid guessed-ID differences and avoid leaking restricted key or bodycam details. Bodycam inventory carries device identity/condition only; footage and evidence stay with an authorised external evidence system, with any future link separately approved.

Proposed write operations: `register_asset`, `receive_stock`, `issue_asset_or_stock`, `transfer_custody`, `return_asset_or_stock`, `acknowledge_handover`, `record_inspection_or_fault`, `adjust_stock`, `send_or_receive_repair`, `retire_asset`, and `correct_event`. Each route binds actor from authenticated AuthIdentity → Person, checks explicit capability plus exact source scope and class, validates recipient/holder, and calls a narrow guarded RPC. Database guard repeats policy, locks item/lot and current custody or balance, checks expected revision, writes business event and new projection atomically. Idempotency key is unique per actor, target and action; same payload replay returns the committed result, changed payload conflicts. Concurrent issue/transfer/return or stock decrements serialize; stale writes return a safe conflict for reload. Direct authenticated inserts/updates/deletes on asset, ledger and projection tables are revoked with RLS enabled; service-role server code is not a business-policy bypass. No client-supplied actor, current balance or approval state is trusted. Audit privileged reads/changes separately from immutable custody history.

## UX and accessibility

Office desktop register: filter by class, status, holder context, location, overdue and stock threshold; show item reference, condition, current holder, expected return and exact last event. Detail separates Overview, Custody, Inspections and History. Stock view groups uniform size and unit with on-hand, available, issued and quarantined counts; distinguish counted from unverified quantities. Operations issue/return uses a review screen naming exact holder, component list, quantities, condition, expected return and any restricted handling before committing. A lost response shows committed receipt or explicit retry state. Staff **My Equipment** lists own issued items and acknowledgement/dispute actions; Site/Event view uses minimal aggregate presence and due items. Overdue and low-stock queues show owner and next action but do not infer fault or auto-reorder.

At 390px use stacked item cards, clear holder/condition/return labels, large controls, no horizontal scroll and no hidden action behind hover. Use the app's blue/graphite/neutral tokens, **no green** status semantics; pair text and icon with contrast. Keyboard focus, logical headings, form labels/errors, confirmation of destructive/exceptional actions, screen-reader announcements and date/time with Europe/London context are required. Restricted key names and personal custody information must not appear in notifications or shared Site/Event cards.
