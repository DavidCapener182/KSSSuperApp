## 1. Outcome, boundary and current facts

Design one controlled notification platform that can accept typed events from existing business sources, resolve exact recipients, and present an in-app Action Centre item while preserving source authority and lifecycle. The approved first source is `DEPLOYMENT_CREATED` for an Event allocation, addressed to its exact allocated Staff Person. The implementation sends in-app only. Email, SMS and push remain later adapters; no vendor or delivery service has been selected.

Potential sources are allocation/Staff response, Event or shift creation/change/cancellation, availability conflict, document request/rejection/replacement, onboarding action, controlled acknowledgement, CRM follow-up due/overdue, staffing gap, and Office review/verification. These are a source catalogue, not a list of approved event producers. Do not implement them all. No generic UI-send endpoint, arbitrary recipient field, bulk blast, free-form message composer, or private payload dump is proposed.

The accepted shared `tasks` table is accountable work with its own lifecycle and typed source rules. It is not a delivery queue. TASK-07B composes allocation, response and availability facts into Workforce and My Schedule but creates no mutable rota. TASK-08A's Dev schema and app changes are in progress on the shared checkout; its final delivery report is the required source-contract handoff. TASK-06C keeps ALLOCATED/ACCEPTED/DECLINED/CANCELLED distinct, and 07A keeps availability independent. TASK-09A attendance remains a separate source and sends no notification in this slice.

## 2. Three different domain records

| Concept | Meaning | Lifecycle owner | Must not imply |
|---|---|---|---|
| **Task** | Accountable work for an exact assignee and source, such as reviewing a submitted document | Existing source-specific Task rules (`OPEN`/`DONE`, and later approved terminal rules) | That a notification was delivered/read, or that a business decision happened |
| **Notification** | A controlled attempt to inform an exact recipient about a typed source event through a channel | Notification delivery subsystem | That the recipient saw it, completed work, accepted a shift or changed a business record |
| **Action Centre item** | In-app presentation of an eligible notification, optionally linked to an existing Task or business record | In-app presentation/read-state rules | A Task, a business record, or an authorisation grant |

Read, unread, dismissed and history state only affect presentation. They never mutate a Task, allocation, document review, onboarding verification, CRM Task, Event, shift demand, availability or attendance. Dismissal cannot complete or cancel source work. A notification may link to an existing Task; it must not silently create a duplicate Task. My Work remains the accountable Task destination and distinct from the Action Centre.

## 3. Controlled source event contract

Propose a closed, versioned event registry owned by server/database source adapters. Initial example kinds for design purposes are `DEPLOYMENT_CREATED`, `DEPLOYMENT_CHANGED`, `DEPLOYMENT_CANCELLED`, `DOCUMENT_REQUESTED`, `DOCUMENT_REJECTED`, `ONBOARDING_ACTION_REQUIRED`, `CRM_TASK_DUE`, and `AVAILABILITY_CONFLICT`. Kinds such as `SITE_SHIFT_CREATED/CHANGED/CANCELLED` can be registered with 08A's exact `site_shift_demand_id` only after 08A approval. Do not emit attendance kinds until 09A is read and reconciled; potential future reminder, no-show escalation and supervisor-attention types require separate source policy. Registry versioning prevents a code deployment from silently changing recipient or payload meaning for an existing event.

Each producer contract identifies: controlled kind and version; exact source record identity and committed source revision/event identity; allowed cause transition; deterministic recipient resolver version; safe template key and bounded typed parameters; optional exact Task reference; and a dedupe identity. It accepts no caller-supplied arbitrary Person audience, destination URL, raw body, attachment, source payload JSON or private note. Validate event/source pairing against authoritative rows and a real committed transition. Unknown kind/version, malformed pairing, uncommitted source transition and unsupported template fail closed.

Suggested event identity: unique `(source_kind, source_id, source_event_key)` where `source_event_key` is an immutable source event UUID, or a typed transition sequence/revision plus event kind where that source has no event UUID. A guarded producer must not use the notification row ID or request-attempt ID as identity. For sources with no durable business event row, define one narrowly scoped event ledger in the same transaction as the guarded transition; do not synthesize identity from wall-clock time or mutable text. This exact identity needs source-by-source validation before implementation.

## 4. Exact recipient resolution and lifecycle

Recipient resolution is server-side, deterministic, and source/action-specific:

| Source event | Proposed recipient rule |
|---|---|
| Allocation / deployment response | Exact `people.id` on the affected allocation (the allocated Staff Person); a manager event may name only the exact authorised actor/assignee defined by its source contract |
| CRM follow-up due/overdue | Exact current Task `assignee_person_id`, after active-role and source Task validation; due timing is derived from that Task and requires an approved scheduler policy |
| Document review request | Exact currently accountable Office reviewer from the accepted document source rule; no broader Office group implied |
| Document rejection/replacement | Exact target Staff Person on that document request/version |
| Onboarding action | Exact active case Person or exact accountable Office owner/reviewer from the case's guarded assignment rule |
| Staffing gap | Only an explicit, currently authorised operational audience for the exact Event requirement or Site shift; do not infer audience from SiteAssignment, Person/Site discovery or general Operations membership |
| Future static shift | Exact allocated Staff Person for allocation events; any gap/reconciliation audience must be explicitly specified under approved 08A scope |

Resolving or searching a Person, Site, Event, CRM record, Task or document is not recipient authority. Check source action authority, current role assignment and exact record scope when resolving; record the rule/version and minimal resolved recipient IDs. Recheck current recipient and source state at dispatch. If a Task is reassigned, role expires, allocation is cancelled, source is superseded, or recipient no longer qualifies, suppress or safely reroute only if the source contract explicitly authorises a new exact recipient. Never silently broaden to a team. A source cancellation/change should invalidate queued stale notification work and either suppress it or produce a distinct typed update; it must not rewrite a previously delivered event.

An external receipt means a provider accepted/processed a delivery attempt, not that a human read it. Keep state narrowly separated: source event recorded; notification queued; channel attempt state (`PENDING`, `DELIVERED`/provider-accepted, `FAILED`, `SUPPRESSED` as needed); in-app read/dismiss state. `READ` and `DISMISSED` are in-app per-recipient presentation state only. Avoid a single ambiguous global `READ` or `DELIVERED` field across channels. Retries append/update attempt state for the same notification identity under bounded retry policy; they never duplicate the logical event or change the source record.

## 5. In-app Action Centre first; later channel adapters

The first implementation slice, if approved, should create only an in-app Action Centre for one low-sensitivity, source-backed type after its producer and recipient policy are chosen. Proposed initial candidates are an exact Staff allocation request or an Office CRM Task due reminder; David must choose one. Document rejection, sensitive availability details and staffing gaps should not be presumed safe merely because the channel is in-app. Do not include push/email/SMS or scheduler until separately approved.

Later email/SMS/push adapters consume the same typed notification and per-channel policy. Provider remains unknown: do not assume Twilio, SendGrid, Resend, Outlook, Firebase, APNs or any other service. Adapter configuration, consent/legal basis, sender identity, cost, regions, retention, credentials, bounce/complaint handling, rate limits, delivery receipts and operational ownership are open decisions. Each channel needs its own recipient eligibility, content minimisation, retry and suppression rules; adding one does not authorise sending. In-app must continue to work independently when an external provider is unavailable.

Action Centre sections: **Unread**, **Requires action**, **Recent**, and **Dismissed/history**. “Requires action” is derived from the currently authorised source or linked OPEN Task, not notification read status. Show a relation to the exact existing Task where one exists, with a separate My Work link. Notification actions are navigation only; business actions remain on source pages and use their existing guarded operations. Badge count is a bounded count of current in-app unread entries for the signed-in Person, not a count of open Tasks or all historical notifications.

At 390px, cards show concise source, safe title, time, text/icon status, and a clear open action; avoid horizontal scroll and dense tables. On narrow lock screens or later email/SMS, preview text must be generic and safe, e.g. “You have an update in KSS Enterprise. Sign in to view it.” Never show protected details on a phone lock screen. Use the existing iOS-inspired shadcn/ui blue, graphite and neutral style; status uses words/icons as well as colour and there is **absolutely no green**.

## 6. Payload privacy, deep links and audit

Persist only bounded template parameters and safe text necessary to render the notification: controlled event type/version, exact source reference, exact recipient Person ID, optional Task ID, safe display template key, source revision/event key, timestamps and delivery state. Do not snapshot source payloads. Never place private evidence, filenames/comments, HR or SIA details, addresses, phone/email, sensitive notes, onboarding comments, CRM private notes, contact details, or credentials/tokens in event payloads, notification text, logs or audit rows. Even in-app content must be least-detail by default.

Notification links are opaque or server-resolved internal route references, not arbitrary URLs. On open, independently authenticate and re-authorise the current user for the exact Task/source/action and reload current safe data. Notification visibility never grants source read authority. Guessed or stale IDs, changed parent IDs, expired roles and revoked assignments fail closed without disclosing record existence. A stale notification may render a generic “This update is no longer available” state. Source files use their existing separate document/storage authorisation.

Use existing `audit_events` or the approved bounded audit pattern for event creation, exact resolver version/result, channel attempt, suppression, read/dismiss transition and administrative retry/suppression, recording actor/time and IDs/status only. No secret payload, message body, external provider token/response body or private note. Audit source event creation separately from delivery attempts; immutable source history remains authoritative for the business change. Decide exact audit retention and access under the project's existing audit policy before implementation.

## 7. Idempotency, concurrency and preference boundary

Create the logical notification idempotently from the deterministic source-event identity and exact recipient/channel policy. Enforce unique keys in the database and do resolver/insert work in a transaction or equivalent atomic claim. RPC/server/worker retries, duplicate callbacks and simultaneous producers must return/reuse the same logical event and must not produce duplicate Action Centre rows or channel sends. If a single source event can legitimately target multiple Persons, uniqueness includes exact `recipient_person_id`; only the typed resolver may enumerate that finite set. Never use recipient-provided idempotency keys.

External send cannot be made exactly-once merely by a local transaction. If later adapters are approved, use a durable outbox/attempt row, stable provider idempotency key where supported, lease/claim with expiry, bounded retry/backoff and append-only provider receipt metadata. Document delivery ambiguity when a provider accepts a send but the response is lost; do not claim exactly-once human delivery. Keep provider payload minimal and safe; provider webhook authenticity and replay protection require separate design.

Keep preferences small: channel opt-in/availability and optional non-operational category controls, keyed to stable Person identity; never key to AuthIdentity. User preference can suppress optional convenience reminders but cannot suppress mandatory operational/security notices where policy says delivery is required. Define which types are mandatory and any legal basis before enabling external channels. Preference edits never alter Task/business state and cannot create an alternate recipient route. Defaults, consent, quiet hours, delivery windows, retention and account closure remain open decisions.

## 8. Proposed schema and guarded interfaces

Validate names against current schema before any future implementation. Prefer additive, source-controlled migration(s), no rewrite of accepted tables:

- `notification_source_events`: stable ID; controlled event kind/version; typed source kind/ID and durable source event key/revision; emitted timestamp; safe bounded parameters; exact producer attribution; unique deterministic source identity. Validate exact source-kind relationship in a narrow private adapter because a polymorphic source pair alone has no FK.
- `notifications`: stable logical ID; source event FK; exact `recipient_person_id`; controlled template key; safe bounded render parameters; lifecycle timestamps; optional exact existing `task_id` reference. Unique per source-event/recipient/presentation purpose.
- `notification_channel_attempts`: logical notification FK; closed channel code; attempt number/idempotency key; narrow provider reference/status/timestamps; safe error code only. Add only when a channel adapter is approved.
- `action_centre_state`: per notification/recipient in-app `read_at`, `dismissed_at`, created time, with monotonic transitions or typed history. Separate per-recipient state avoids changing shared notification delivery state.
- Optional bounded preference table only after the preference policy is decided; no general settings framework.

**First-slice schema actually delivered:** `staff_in_app_notifications` binds one row to the immutable Event `event_staff_allocation_events.id`, its exact allocation, and exact recipient Person; unique source-event and allocation/type keys make producer retries idempotent. `staff_in_app_notification_events` records only CREATED/READ/DISMISSED actor/time and source IDs. Current Event/Site/role/time/state are reloaded through a self-only projection. No generic source registry, external outbox/attempt, Task link, preference table, or static producer was added; only the initial `ALLOCATED` Event-history insertion can create a notification.

RLS and grants deny direct authenticated table access. Read projections are scoped to `auth.uid()` → active AuthIdentity → stable Person, active role and exact notification/source visibility. Narrow private SECURITY DEFINER producer functions use a fixed safe search path, exact source checks, closed kinds, bounded inputs and database-derived actor/time. Client cannot invoke a function with arbitrary type, recipient and body. The Action Centre read RPC returns only safe fields and must not expose internal/provider payload or another Person's state. Mark-read/dismiss RPCs affect only own in-app presentation state and are idempotent; they cannot mutate Task or source. No service-role shortcut that bypasses end-user checks.

Do not pre-create all future source adapters or add a generic notification engine beyond the first approved event. Source cancellation, reassignment, event retention, deletion/privacy requests, audit retention and provider webhooks need explicit migration/retention design. Index exact recipient plus state/time, source event identity, and attempts by notification/state; bound pagination and badge queries. Do not add summary tables absent measured need.

## 9. Cross-module seams and invariants

TASK-08A's approved implementation seam is a Site Service with materialised dated demand, a configurable eight-week technical horizon, effective-dated `PAUSED`, a shared cross-source Person conflict guard as a hard gate, and typed reconciliation for materialised rows. These are design inputs only; confirm exact shipped contracts from 08A's delivery report before implementing any 08B producer. Static demand creation/change/cancellation and reconciliation should emit the same controlled source-event contract as Event deployments, using exact stable dated-demand, allocation and reconciliation identities; never put ongoing/static shifts on an Event-only route or discriminator. Keep Site Service/template edits separate from the exact dated shift event, and do not notify on generator retries or horizon refresh unless a real typed business transition occurred. A conflict or reconciliation notification may be produced only after its guarded source operation commits, with the exact resolver/action scope and safe summary. The shared Person guard is an allocation correctness gate; it does not itself authorise notification writes or imply delivery.

Read TASK-09A before finalising attendance seam. Later attendance may cause a Staff reminder, a no-show escalation or supervisor attention, but attendance is not implemented here. Such events must use exact stable demand/allocation/attendance records, avoid inferring worked time, and distinguish allocated, accepted, attended, worked and payable states. Do not modify allocation or Task lifecycle merely because a reminder was read/dismissed.

Preserve all accepted invariants: Person != AuthIdentity; Task != business state; allocated != accepted != attended != worked/payable; availability remains a separate declaration; source event != notification delivery; provider receipt != human read. Exact record scope, active role, source authority, private evidence boundaries and safe projections remain enforced server-side and under RLS.
