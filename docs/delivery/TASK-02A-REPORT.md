# TASK-02A report — synthetic private document evidence

**Date:** 23 September 2026. **Project:** dedicated Supabase development project `dnfhkmmnlbiabqypclqg` only. **Scope:** TASK-02A only. **Result:** implemented and development verified; awaiting David's review. No production deployment, live data, external integration or TASK-02B work.

## Delivered

An Office Admin can select a Security Staff Person eligible through an Office-managed Site and create a private document request. Staff can view and submit one synthetic PDF, PNG or JPEG up to 5 MiB. The original Office requester, the target Staff Person and Super Admin can view the submitted record and retrieve bytes through their defined paths. Staff B, Office B, Operations, anonymous and unmapped identities cannot use the request/file path. Site is optional creation context and never the document audience. The UI says `Requested` or `Submitted (not reviewed)`; all files remain `NOT_SCANNED`.

The server reads bounded multipart bytes, checks filename, MIME, extension and signature, hashes the bytes, asks a proof-guarded database function to create or resume a pending version, uploads through the ordinary user-scoped Supabase session, downloads that object to verify exact size/hash, and finalises through a second guarded function. A second submission conflicts; a retry after Storage success can reconcile the same pending version. The object key is random and never exposed in a browser URL. Retrieval uses attachment disposition, `nosniff`, private/no-store responses and a second record check. No signed/public URL is issued. The HMAC signing value stays in ignored server-only `.env.local`.
