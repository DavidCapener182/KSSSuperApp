## One factual attendance domain: forward adapter

Propose a **forward migration** of the existing attendance case/event tables, retaining their IDs and Event FKs. Add `site_shift_allocation_id` to each as a typed FK; make Event FK nullable only with a database XOR constraint requiring exactly one Event or Site Shift allocation. A case is unique per non-null typed source allocation. Keep `person_id` on each record and enforce `(case_id, source allocation ID, person_id)` equality for both variants. The static allocation table has `(id, demand_id)` uniqueness but not an existing `(id, person_id)` unique key; add a narrowly scoped unique constraint/index or equivalent immutable binding guard to support a composite FK on `(site_shift_allocation_id, person_id)`. Verify this against the final schema before migration. Do not rely on a UI discriminator, UUID coincidence or `COALESCE` alone. Case source and Person are immutable after creation; facts inherit them. A fact's correction/resolution targets an event in the same case, source and Person. Keep `attendance_events` append-only and 09A revision numbering per case.

Use an explicit source discriminator (`EVENT` / `SITE_SHIFT`) in RPC inputs and read models, validated against which FK is populated. Existing Event RPC signatures and links must continue to work. Add narrow static wrappers or a carefully reviewed shared private core; do not replace the 09A Event implementation merely to unify code. A static wrapper derives demand and Site Service context server-side from the exact allocation. It must recheck the current allocation, demand and Person binding on each read/action. Historical attendance stays attached to its original source if the demand or Service is later paused/ended/cancelled.

Keep the 09A factual vocabulary and meaning: `CHECK_IN`, `CHECK_OUT`, `NO_SHOW_RECORDED`, `EXCUSED_ABSENCE_RECORDED`, `CHECK_IN_NOT_POSSIBLE`, `REVIEW_REQUIRED`, `CORRECTION`; actual instant, database `recorded_at`, actor, method, reason and correction/resolution links. Store instants as `timestamptz`, display Europe/London with date and zone for overnight/DST cases. A client clock is an input, not proof of location or work duration. Attendance asserts an observed fact only; it does not accept an allocation, infer a break, calculate worked time or approve payable/chargeable minutes.

## Actions and state

Staff online self Check In/Out requires Auth identity mapped to the **same stable Person**, an active Staff role, and the exact static allocation currently `ACCEPTED`. An `ALLOCATED`, `DECLINED` or `CANCELLED` row cannot be implicitly accepted by the attendance action. Check Out requires a valid preceding Check In under the accepted 09A sequence rules. The server and guarded database operation recheck source status in the same transaction as the fact append. A scheduled time or Action Centre notification is never attendance evidence.

An authorised Office/Operations/Super Admin actor may record an observed check-in/out or a reasoned no-show, excused absence or check-in-not-possible fact only for a source within their exact operational Site Service/Site scope and action permission. Job title or allocation ownership alone is not a permission. Manager observations identify the observer, mode, actual time and database record time. Corrections append a reasoned new event referencing the exact prior fact; the original remains visible. A late check-in following a recorded no-show needs an explicit attributable resolution, as in 09A. No silent replacement of observed times or exception history. Manager actions require a current source/permission check; historical reads remain bounded to authorised scope.

If a static allocation is cancelled after attendance exists, preserve the case/facts and append one idempotent `REVIEW_REQUIRED` source-cancellation fact. Block further Staff self action; a manager can review/correct historical facts under scoped authority. If demand cancellation or Service lifecycle change occurs without allocation cancellation, surface the changed source state for review and block new Staff self actions according to the same transactionally checked validity rule; do not retarget or delete history. Define the exact demand/Service transition trigger and duplicate suppression in implementation after reviewing 08A's cancellation paths. Source cancellation before any attendance does not require manufacturing a case solely to display history. A replacement allocation never inherits an old case.

## Concurrency, idempotency and access

For every write, lock the exact typed source allocation and attendance case in a consistent order, check current source/Person/status and expected case revision, then append in one transaction. Case creation is unique per typed allocation. Bind actor from the authenticated session, not request body. Use actor + case + action + idempotency key with a payload fingerprint: a lost response replay returns the committed fact, while key reuse with changed payload fails. Concurrent Staff/manager Check In must yield one current check-in, not two; stale corrections return a safe conflict/reload. Serialise cancellation against action so either the action commits before cancellation and is followed by review, or cancellation wins and the action is denied. Event and static cases must stay source isolated even when UUIDs or dates are deliberately substituted in requests. The shared allocation Person lock/overlap guard remains unmodified.

Enable RLS for any changed/new objects and deny direct authenticated table reads/writes. Public `SECURITY DEFINER` RPCs need fixed empty search path, explicit Auth Person/role/action/source checks and least-privilege projections; private helper execution must not be exposed. Repeat checks in API routes. Service-role use cannot skip business guards. No caller-supplied actor, Person, demand or Service may authorise an action. Staff see only their own rows and safe reason codes/history; suppress manager free-text notes as 09A does. Managers see only scoped operational attendance data, with reason text only where needed for their review. Do not expose contact details, HR/SIA/onboarding evidence, CRM detail, rates, money, peer records, raw audit payloads or cross-scope counts through list, focus, search, export or errors. No linked private file inherits attendance audience.
